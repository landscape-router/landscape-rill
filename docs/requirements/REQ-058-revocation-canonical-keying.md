# REQ-058 吊销与身份比对的键规范化（canonical keying）

> 类型：需求 ｜ 状态：✅ merged ｜ 提出：2026-09-02 ｜ 合并：2026-09-02
> 去向：CONTROL_PLANE §3.5/§3.1 ｜ 验收场景：SEC-30 ｜ lessons：KC-06（本条 lesson 化）

## 动机

外部同类协议实现的公开缺陷：吊销/黑名单机制以**签名/证书的可变编码字节**作为识别键，攻击者利用签名可塑性（malleability）改写编码但不改变语义 → 吊销条目失配 → 已吊销身份绕过黑名单继续入网。根因不在签名算法本身，而在**识别键选在了非规范的编码形式上**。

mesh 的吊销体系（CONTROL_PLANE §3.5）当前以 node_id（4B 定长）为吊销键、以原始公钥字节做绑定比对——天然规范，未踩坑。但这是**隐式安全**：规则没有写进设计，未来扩展随时可能把可变编码字节带进索引/比对路径（联邦条目交换重签、ACL v2 策略键、任何引入证书结构的演进）。

## 决策摘要

1. **硬规则**：凡参与吊销索引、身份比对、去重的键必须是**规范形式**——语义等价的两种编码必须解析出同一个键
2. mesh v1 具体化：吊销键 = node_id；身份绑定比对 = 原始公钥字节（Ed25519 确定性签名，无可塑性面）；不引入"按签名/证书编码识别条目"的机制
3. 延伸约束：联邦 v2 条目识别键不得含签名字节（重签后识别必须稳定）；ACL v2 subject/object 键同理；未来任何证书/签名结构参与索引前先规范化或以内容摘要为键

## 去向

- **CONTROL_PLANE §3.5**：吊销键 = node_id + 禁止签名编码键（延伸约束常驻复核触发点：lessons KC-06）
- **CONTROL_PLANE §3.1**：身份比对键 = 原始公钥字节，binding 字节不参与索引/比对
- 验收场景：SEC-30（[tests/security/control-plane-attacks.md](../tests/security/control-plane-attacks.md)）
